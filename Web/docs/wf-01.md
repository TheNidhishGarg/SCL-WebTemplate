# WF-01: Client brief and website specification

WF-01 records what a project must deliver. Its one output is an **approved, versioned client brief plus the client's asset register**, handed to WF-02 through WF-10 in a fixed, validated format.

## What it does

| Capability | Where |
| --- | --- |
| Dashboard: projects, stage, completeness, next actions, recent activity | `/projects` |
| Create a project (client/business name, project name), then fill in the brief | `/projects/new` → `/projects/:id/brief` |
| Brief editor with draft saving, live completeness, field-level validation, approval | `/projects/:id/brief` |
| Revise an approved brief as version n+1 (the old version stays in force until approval) | `/projects/:id/brief` |
| Asset/reference register: upload files or record links | `/projects/:id/assets` |
| Project overview, details editing, handoff | `/projects/:id` |
| Handoff JSON for downstream modules | `GET /api/projects/:id/handoff` |

The brief captures the deliverable (conventional website, cinematic journey, or both), industry, current website URL, summary, target audiences, business objectives, required pages, desired visitor actions, reference websites, cinematic intent/runtime/branching (only when a journey is included), languages, launch date and other constraints.

## Lifecycle

```
create project ──► brief v1 (draft) ──save──► draft ──approve──► v1 approved ──► handoff available
                                                                   │
                                                          start revision
                                                                   ▼
                                                    v2 (draft; v1 still approved) ──approve──► v2 approved, v1 superseded
```

- A **draft** can be saved at any time, half-written. It is checked for types and size limits only.
- **Approval** runs the full validation (`ClientBriefContent`) on the server. If anything is missing, nothing is approved and the user sees which sections and fields to fix.
- An approved version is **frozen**: its validated content is stored at approval time and never edited again.
- Saves carry the id of the version the editor loaded. If that version is no longer the editable draft (for example it was approved in another tab), the save is refused with a conflict message instead of being applied to the wrong version.
- A project's stage (`brief_in_progress`, `brief_ready`, `brief_approved`, `brief_revision`) is derived from the stored brief, never stored separately.

## Interface for WF-02 to WF-10

### The handoff

`GET /api/projects/:projectId/handoff`

| Status | Meaning |
| --- | --- |
| 200 | Approved brief, in the `scl.wf-01.brief-handoff/v1` format |
| 404 | No such project |
| 409 | The project exists but no brief version is approved yet. Downstream modules never receive a draft. |
| 403 | The dashboard is not available on this deployment (see Access) |

Add `?download` to get it as a file attachment.

In-process consumers in this app call `getDashboardStore().getBriefHandoff(projectId)`. It returns the same object, or `null` when nothing is approved.

The schema is `BriefHandoff` in [src/domain/brief-handoff.ts](../src/domain/brief-handoff.ts). Consumers should:

1. Parse the response with `BriefHandoff`, not trust it.
2. Record `brief.id` and `brief.version` on whatever they produce, so every downstream output says exactly which brief it was built from.
3. Treat `schema` as the compatibility contract. A breaking change ships as `.../v2` alongside v1, never as an edit to v1.

### What each module reads

| Module | Reads from the handoff |
| --- | --- |
| WF-02 Reference acquisition | `content.referenceUrls`, `content.websiteUrl` |
| WF-03 Source analysis | WF-02's captures; `content.requiredPages` for scope |
| WF-04 Brand configuration | `assets` (logo, font, brand_guidelines, photography), `content.constraints.items` with category `brand` |
| WF-05 Content and pages | `content.requiredPages`, `content.audiences`, `content.objectives`, `content.constraints.locales` |
| WF-06 Journey planning | `content.cinematic` (present only when `deliveryMode` is `cinematic` or `combined`), `content.audiences` |
| WF-07 Video production | WF-06's manifest; `assets` of kind `video` and `photography` as source material |
| WF-08 Integration | `content.deliveryMode` |
| WF-09 Conversion and analytics | `content.desiredActions` |
| WF-10 QA and deployment | `content.constraints` (launch date, technical and legal items), `brief.version` for release records |

A conventional project (`deliveryMode: "conventional"`) has `cinematic: null`, and WF-06/07 do not run. WF-02 to WF-05 never depend on the cinematic fields.

### Asset files

`GET /api/projects/:id/assets/:assetId/file` always serves an attachment (`application/octet-stream`, `X-Content-Type-Options: nosniff`), so an uploaded SVG or HTML file cannot run in the dashboard's origin. Uploads are limited to 25 MB, with an extension allowlist per kind. Larger media should be recorded as links; generated media belongs to WF-07 and Mux.

## Persistence

- **Store:** Node's built-in SQLite (`node:sqlite`), at `$SCL_DATA_DIR/scl.sqlite`. Uploaded files are stored under `$SCL_DATA_DIR/uploads/<projectId>/<assetId>`. Storage keys never contain the client's filename.
- **Schema:** [src/server/store/db.ts](../src/server/store/db.ts). Append-only migrations, applied on startup. Constraints enforce one draft and one approved brief per project, the approval invariants, and upload/link consistency.
- **Boundary:** only [src/server/store/store.ts](../src/server/store/store.ts) touches SQL or the upload directory. Moving to a hosted database replaces that module and nothing above it.
- **Failure behaviour:** every write is one transaction, including its activity-log entry. A failed upload removes its file, so there is never a record pointing at nothing or a stray file without a record. The UI shows success only after the commit. Unexpected failures show "Not saved…" with a log reference, never internals.

Why SQLite rather than Postgres/Supabase now: no database for this project exists yet (none of the connected Supabase projects is SCL's), and WF-01 had to be persistent and testable locally today. The SQL is kept portable (text ids, ISO timestamps, JSON in text columns, CHECK constraints) for the move.

## Access

**There is no sign-in yet.** The dashboard serves freely in development. Outside development, every page, Server Action and API route refuses (pages show "Dashboard unavailable", APIs return 403), and the database is never opened, unless `DASHBOARD_ALLOW_UNAUTHENTICATED=true` is set. That flag is for a private network only. On Vercel the server refuses to start, because the local store cannot persist there.

## Before production deployment

1. **Hosted database and file storage.** Choose them (Supabase Postgres + Storage is the likely fit; the existing OB-01 workflow already uses Supabase), then port `store.ts` and the migrations.
2. **Authentication and project isolation.** Choose sign-in (Supabase Auth, or SSO with the SCL Dashboard), replace `requireDashboardAccess()` with a real user check, and scope projects to an organisation.
3. **Link to the SCL Dashboard.** `projects.dashboard_client_id` exists, but nothing sets it yet. Decide whether projects are created from the dashboard's clients or linked afterwards.
4. **Machine access to the handoff.** n8n or other services need a service token for `/api/projects/:id/handoff`. Today the handoff has the same access rule as the dashboard.

## Limitations

- No authentication or roles; anyone who can reach a dev server can edit. "Approve" is a single action, not a separate reviewer step (`pending_approval` exists in the model, unused).
- SQLite on local disk: a single server process, no Vercel. Back up `$SCL_DATA_DIR`.
- No project archiving, no project or brief deletion, no diff between brief versions.
- Uploads are buffered in memory (25 MB cap). Large media should be links.
- An unknown project id renders the not-found page with HTTP 200 and `noindex`. Next.js streams pages that have a loading state, so the status is sent before the lookup. The handoff API returns a real 404.
- Accessibility has been built for (labels, error association, focus management, keyboard-operable controls, reduced motion) but not audited with assistive technology or an automated checker.
