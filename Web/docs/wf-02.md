# WF-02: Reference website acquisition

WF-02 builds a project's **reference library**: the pages the client and team want to learn from, what was actually acquired from each one, and what people saw or concluded. Its output is a documented export that WF-03 reads.

## What it does

| Capability | Where |
| --- | --- |
| Library: references grouped by site, status counts, filters by status, client page and observation aspect | `/projects/:id/references` |
| Import the approved brief's reference websites (re-runnable; skips ones already present) | library page |
| Add references by hand (one page per reference, many per site) | library page |
| Reference detail: evidence, observations, inferences, acquisition actions, organisation | `/projects/:id/references/:refId` |
| Export for WF-03 | `GET /api/projects/:id/references/library` (`?download` for a file) |

## Three kinds of record, never mixed

| Kind | What it is | Who creates it | Editable? |
| --- | --- | --- | --- |
| **Evidence: attempts** | Each acquisition attempt and its outcome: system URL checks, people's capture attempts | System or a person, labelled as such | No. Append-only, so a failure stays on record after it is resolved |
| **Evidence: captures** | Files captured from the page: SaveMyResources archives, screenshots, with tool, capture date and SHA-256 | A person | Can be deleted, not edited |
| **Observations** (`observed`) | What a person saw on the reference, optionally tied to a capture | A person | Yes |
| **Inferences** (`inferred`) | Interpretations: a person's ("probably GSAP"), or a URL check's ("looks like a sign-in page") | A person or the check | A person's: yes. A check's: no |

Observations are organised by **aspect**: section, interaction, layout, visual style, content pattern, or other. References are organised by **site** (host), **page type** (free text, e.g. "Pricing"), and the **client pages** they inform. Those are slugs from the approved WF-01 brief and are validated against it.

## Acquisition status

Derived from the records, never stored:

| Status | Meaning |
| --- | --- |
| `pending` | Nothing attempted yet |
| `checked` | The URL check reached the page, but nothing has been captured |
| `captured` | At least one capture file exists |
| `failed` | The attempt the status rests on failed (blocked, restricted, not found, unreachable, capture failed, …) |
| `manual` | A person marked it as not acquirable, with a reason, and records observations by hand |

The status rests on the newest attempt that still stands. If every capture is deleted, the "captured" attempt no longer counts, and the status falls back to the attempt before it. The page always explains a failed status using that same attempt.

**Recovering from a failure** (shown on the page whenever a reference has failed):
1. Check the URL again. Sites come back.
2. Capture the page yourself with SaveMyResources from a browser that can open it, then upload the archive. The status becomes `captured`, and the earlier failures stay in the log.
3. Mark it for manual observation, give the reason, and record what you can see.

## The URL check

**Check URL now** makes one ordinary GET request from the server. It does not sign in, sends no cookies, and does not retry. It records the HTTP status, every redirect, the final URL, the content type and the page title. It reads at most 512 KB, only to find the title and whether there is a password field, and **stores none of the page**.

What it reports, and does not do:
- 401/403 → `access_restricted`; 404/410 → `not_found`; 429 → `rate_limited`; 5xx → `server_error`; DNS, connection, TLS or timeout errors → `unreachable` with the reason; more than 5 redirects → `redirect_loop`.
- A sign-in page (by URL or a password field), or a bot-check page (by title), is recorded as an **inference**, not as the reference's content. The page may well be reachable while what was reached is not the reference.
- It never tries to get past sign-ins, paywalls or bot protection.

**Server protection.** Because the check fetches addresses that users type, it refuses private, loopback, link-local (including cloud metadata at 169.254.169.254), carrier-grade NAT and reserved addresses. This is enforced at connect time, through a custom DNS lookup, so a hostname that resolves to an internal address is refused even if it changed after it was entered. Redirects are followed by hand and re-checked at every hop. Only ports 80 and 443 are used. A refused URL is recorded as `blocked_by_policy`, which is a failure, so it is visible and recoverable by capturing manually.

## SaveMyResources: manual steps

SaveMyResources is used **by a person, in their own browser**. This app has no integration with it, and does not assume it has an API. **To confirm:** the exact tool and version the team uses. These steps assume a browser extension that saves a page's loaded resources as a .zip archive. If it works differently, update this section and the in-app instructions on the reference page.

For each reference:
1. Open the page in a browser. Only capture pages you are allowed to open. Do not get around sign-ins, paywalls or bot checks, and do not use someone else's account.
2. Let the page load fully and scroll to the end, so lazy-loaded resources are fetched.
3. Run SaveMyResources to save the page's resources. It produces a `.zip`.
4. Take a full-page screenshot as well (Chrome DevTools → Run command → "Capture full size screenshot").
5. On the reference page, under **Add a capture**, upload the archive (kind: *Resource archive*, tool: *SaveMyResources*) and the screenshot (kind: *Screenshot*), with the date you captured them and a note on what they cover (e.g. "homepage, logged-out view").
6. If capturing fails, use **Record a failed capture** and say what happened.
7. Add observations, choosing *Observed* or *Inferred*, and link them to the capture they came from.

Limits: archives up to 200 MB (`.zip`; `MAX_CAPTURE_BYTES`, 209,715,200 bytes, inclusive); screenshots `png/jpg/webp/pdf`; other captures `html/mhtml/txt/mp4/webm/mov` and the above. The archive is stored as is: WF-02 does not open or inspect it. Downloads are always served as attachments with `nosniff`, so captured HTML or SVG can never run in the dashboard.

## Copyright and access

References are **research inputs, not permission to reuse**. The export carries the notice: *"Research input only. Captured material remains the property of its owners; it may inform structure and direction but must not be copied into client work without permission."*

Record the owner under **Attribution**. Captured archives can contain proprietary code, copy and images. WF-03 may study their structure, but must not copy protected material into client work. Delete captures that are no longer needed.

## Interface for WF-03

`GET /api/projects/:projectId/references/library` → `scl.wf-02.reference-library/v1`. The schema is `ReferenceLibrary` in [src/domain/reference-library.ts](../src/domain/reference-library.ts). In-process: `getDashboardStore().references.library(projectId)`.

| Status | Meaning |
| --- | --- |
| 200 | The library (possibly with zero references) |
| 404 | No such project |
| 403 | Dashboard not available on this deployment |

```jsonc
    "inferred": [
      { "source": "person", "aspect": "interaction", "text": "…", "observationId": "…", "attemptId": null, "at": "…" },
      { "source": "url_check", "aspect": null, "text": "The final URL looks like a sign-in page…", "observationId": null, "attemptId": "…", "at": "…" }
    ]
  }]

```

How WF-03 should use it:
- Parse with `ReferenceLibrary`, and record `generatedAt` and the reference ids it analysed.
- Analyse source code only from `evidence.captures` of kind `archive`. Verify `sha256` after download.
- Weight the records: captures > `observed` > `inferred`. Treat `inferred` as leads to verify.
- References with status `failed`, `pending` or `checked` have no captured material. Use their observations, or skip them; never fill the gap with guesses.
- Map `targetPages` to `brief.requiredPageSlugs`. A slug may stop being in the list after a brief revision; WF-02 validates slugs only when a reference is edited.
- Nothing in the export depends on WF-02's storage. There are no storage keys or table shapes. A breaking change ships as `/v2`.

## Persistence

Four tables, created by migration 2 in [src/server/store/db.ts](../src/server/store/db.ts): `reference_sources`, `reference_attempts` (append-only), `reference_captures` and `reference_observations`. Code is in [src/server/store/references.ts](../src/server/store/references.ts). Files are stored under `$SCL_DATA_DIR/uploads/<projectId>/references/<referenceId>/<captureId>`.

As in WF-01: every write is one transaction with its activity entry, files are written before their row and removed if the row fails, and deleting a reference removes its files. The network call in a URL check runs outside any transaction. Its result is recorded only if the reference still exists when the check finishes.

## Limitations

- No SaveMyResources integration, by design (see above). Capturing is manual.
- **SaveAllResources** is integrated. The primary path is **Generate Website Template** on the project page: Web runs SaveAllResources on a URL and registers the resulting website-template.zip as a capture here and a WF-03 source. Alternatives on the references page: capture with the browser extension, or import an existing SaveAllResources ZIP (manual fallback). See [save-all-resources.md](save-all-resources.md).
- The URL check sees what an anonymous server sees. Sites that block datacenter traffic, or render only in a browser, may report `access_restricted`, or reach a page without the content. Capture those manually.
- Archives are opaque to WF-02. Whether an archive is complete is for WF-03 to judge.
- No bulk actions (check all, import a list). Uploads are buffered in memory (200 MB cap); downloads are streamed.
- Same access model as WF-01: no sign-in. See [wf-01.md](wf-01.md#access).
