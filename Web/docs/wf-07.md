# WF-07: AI video asset production

WF-07 produces the media an **approved WF-06 journey version** needs. It generates takes with Runway or Veo, or takes uploads made in Flow or any other tool. It checks each take, and a person reviews and approves it. The result is a scene-to-asset manifest for WF-08. Everything here happens **before publication**: nothing is generated per visitor, and WF-07 doesn't touch the live journey runtime (WF-08, not built).

## Where

| URL | What |
| --- | --- |
| `/projects/:id/production` | Productions, provider configuration status, start a production from an approved journey version |
| `/projects/:id/production/:productionId` | The queue by scene and shot: prompts, generation, jobs, uploads, takes, review, blocking |
| `GET /api/projects/:id/production/:productionId/asset-manifest` | `scl.wf-07.asset-manifest/v1` for **WF-08** (`?download` for a file) |
| `GET /api/projects/:id/production/:productionId/takes/:takeId/file` | A take's original bytes, inline for playback, with Range support (`?download` for an attachment) |
| `POST /api/projects/:id/production/:productionId/shots/:slotId/upload` | Manual upload (multipart: `file`, `tool`), up to 500 MB |

## Model

Code: [src/domain/production.ts](../src/domain/production.ts) and [src/server/store/production.ts](../src/server/store/production.ts).

- **Production:** one for each approved journey version. It freezes a copy of that version's scene manifest, so later journey edits never change what's being produced. A new approved version needs a new production.
- **Shot:** one for each asset slot in the manifest. A shot carries the slot's acceptance criteria: aspect ratio, minimum duration, whether it must loop, and no burned-in text.
- **Prompt versions:** v1 is copied from the scene's prompt. "Save as new prompt version" adds v2, v3 and so on, with a note. Every job records the prompt version it used, and so does every take.
- **Job:** one provider request. It stores the provider, model, prompt version, the request as sent (image data replaced by its hash and length), the provider's job ID, the attempt count, and any error with whether it's retryable. Job states:

  | State | Meaning |
  | --- | --- |
  | `queued` | Recorded, not yet accepted by the provider |
  | `generating` | The provider accepted it and returned a job ID |
  | `completed` | The output was **downloaded, probed and stored as a take**. A provider's "succeeded" alone never sets this. |
  | `failed` | The provider rejected the job, the generation failed, or the download failed. The error is stored. |
  | `canceled` | Cancelled here. The provider may still finish the job and bill for it, and the UI says so. |

- **Take:** a stored file. It's either a provider output or a manual upload with the tool named, such as "Flow". Each take has automatic checks and a review state: `review_required`, `approved`, `rejected` (needs a note), or `superseded` (it was approved, then a later take replaced it). Originals are never modified or deleted. Rejected and superseded takes stay listed.
- **Shot status** is derived, not stored. It's one of: not started, queued, generating, failed, review required, approved, all takes rejected, blocked. **Blocked** needs a reason. An approved shot can't be blocked until its take is rejected.

## Checks

Automatic checks run on the bytes. Nothing the provider or the uploader *says* about a file is trusted. The probe is [src/server/production/media.ts](../src/server/production/media.ts).

| Check | How |
| --- | --- |
| size | Must be between 1 byte and 500 MB |
| format | MP4/MOV with a `moov` header and a video track for `video`/`loop` slots; PNG or JPEG for `still`; an audio track for `audio` |
| duration | From `mvhd`. It must be at least the slot's minimum, with 0.1 s tolerance. |
| dimensions | From the video track's `tkhd`. The aspect ratio must be within 3% of the slot's. |

The server can't decode frames, so the **reviewer confirms** three things when approving: the whole take plays correctly, no text, caption, logo or interface element is in frame, and (for loop slots) the loop is seamless. Approval is refused if any check fails or any confirmation is missing.

## Providers

The adapters are in [src/server/production/providers.ts](../src/server/production/providers.ts), behind one interface: `build`, `submit`, `poll`, `download`. The store never calls a provider inside a database transaction. It records only what the provider returned.

Facts below are from the providers' public docs, checked 2026-10-01. **No credentials exist for this project yet, so neither adapter has been run against the live API.** The adapters are tested against the documented response shapes. Expect to adjust them the first time real keys are used.

### Runway (`RUNWAYML_API_SECRET`)

- `POST https://api.dev.runwayml.com/v1/image_to_video` when the scene has a start keyframe, otherwise `/v1/text_to_video`. Headers: `Authorization: Bearer …` and `X-Runway-Version: 2024-11-06`. The model used is `gen4.5`.
- Body: `promptText` (≤1000 characters), `promptImage` (a data URI ≤5 MB), `ratio` and `duration` (2–10 whole seconds).
- Ratios used: 16:9 → `1280:720`, 9:16 → `720:1280`. Image to video also supports 1:1 → `960:960`, 4:3 → `1104:832`, 3:4 → `832:1104` and 21:9 → `1584:672`. Text to video supports 16:9 and 9:16 only.
- Polling: `GET /v1/tasks/{id}`. `PENDING`, `THROTTLED` and `RUNNING` count as running. `SUCCEEDED` gives the output URL. `FAILED` is not retryable when its `failureCode` names safety or input problems, and is retryable otherwise.

### Veo 3.1 via the Gemini API (`GEMINI_API_KEY`)

- `POST https://generativelanguage.googleapis.com/v1beta/models/veo-3.1-generate-preview:predictLongRunning` with the header `x-goog-api-key`.
- Body: `instances[{ prompt, image?, lastFrame? }]` and `parameters { aspectRatio: 16:9 | 9:16, durationSeconds: "4" | "6" | "8", resolution: "720p", personGeneration }`. The duration is the shortest allowed value that covers the shot.
- Polling: `GET /v1beta/{operation name}` until `done`. The video is at `response.generateVideoResponse.generatedSamples[0].video.uri` and is downloaded with the key. **Google keeps outputs for 2 days**, so WF-07 downloads them as soon as the job succeeds.

### Both providers

- **Neither provider accepts a negative prompt.** The scene's "avoid" text, including the no-text rule, is written into the prompt as `Avoid: …`, and the request preview says so.
- Scenes longer than a provider's maximum are refused before anything is sent, with the reason. The sample journey's 10–15 s scenes exceed Veo's 8 s for most shots, and its 12 s and 15 s scenes exceed Runway's 10 s. Either split the shot in WF-06 (shorter slots), or make it elsewhere and upload it.
- The server only fetches keyframes stored in the project (uploaded assets and WF-02 captures). External keyframe URLs are never fetched.

### Flow

Flow has no public API, so it's used through its own UI:

1. Open the shot, then copy the prompt and the "Avoid" text from the prompt panel.
2. Generate in Flow at the shot's aspect ratio and at least its minimum duration. If the scene has keyframes, use them as frames.
3. Export the MP4, then use **Manual upload** on the shot with "Made with: Flow". It's checked like any other take.

The same route covers takes made in Runway's or Google's own apps, edited footage, or a shoot.

## Duplicates, failures and retries

- **One active job per shot and provider.** A database index enforces it, so a second **Generate** is refused while one is queued or generating.
- **Identical requests.** Each job has an idempotency key: a hash of the shot, provider, model, prompt version and request. If an identical request already produced a take, generating again needs an explicit "generate another take anyway".
- **Retry** is offered only for failures marked retryable: HTTP 429, 5xx, network errors, internal provider errors, and failed downloads. A job is retried at most 3 times. Moderation and invalid-input failures need a new prompt version instead.
- **A failed status check is not a failed generation.** The job stays `generating`, and the error is shown until the next successful check.
- **Polling** happens when you press **Check status**. There's no background worker yet, so nothing is lost if the server restarts: the provider job ID is stored, and polling resumes from it.

## Export for WF-08

`scl.wf-07.asset-manifest/v1` covers every scene and slot in playback order. Each slot is `approved` (with the asset), `blocked` (with the reason) or `missing`. An approved asset includes:

- its URL, MIME type, size, SHA-256, duration and dimensions
- its source (`provider` or `manual_upload`), provider, model, provider job ID and prompt version
- its approval time

`complete` is true only when every required slot is approved. A blocked slot is explicit, but it doesn't count as complete. Asset URLs point at this dashboard and need dashboard access. WF-08 decides how media is published to visitors; that isn't built here.

## Tests

- `src/server/production/providers.test.ts`: request building and limits, headers, every task and operation state, error classification, downloads, and the media probe, all with a scripted `fetch`.
- `src/server/store/production.test.ts`: success; download failure (never completed); non-retryable and retryable failures; the retry limit; duplicate control; unconfigured providers; manual upload checks; review rules; supersession; blocking; the manifest; project isolation.
- `e2e/wf-07.spec.ts` uses a production build with no credentials. Providers report missing configuration and refuse requests. A preview refuses a 12 s shot for Runway. A wrong-aspect upload fails its checks and is rejected. A Flow upload is approved only after the confirmations. The other shots are blocked. The test then checks the manifest and Range playback.
