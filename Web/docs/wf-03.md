# WF-03: Source-code analysis and template extraction

WF-03 turns authorised source code into three things: an evidence-backed analysis, reusable templates, and a **template manifest** for WF-04 (brand configuration) and WF-05 (pages). It does **not** apply a brand or generate pages. Values found in the source are reported as they were written, and WF-04 decides what the client's brand is.

The work is split by what each side does reliably:

| Who | Does |
| --- | --- |
| **The app** (deterministic scanner) | Inventories files, framework signals, routes, components, styles, assets, dependencies, and security, accessibility, licensing and missing-asset risks. Every item cites a file and line. Same input gives the same report and digest. |
| **A person in VS Code with Claude Code** (analysis kit) | Judgement: templates, interaction behaviour, what the scanner cannot see. Findings come back as JSON and are **checked against the source** before they are accepted. |
| **A person in the dashboard** | Authority, which templates to keep, extraction, build results, answers to open questions. |

## The process

1. **Register a source** (`/projects/:id/sources`):
   - Upload a `.zip` of a repository (`git archive --format=zip -o source.zip <commit>`, or a GitHub "Download ZIP") or of website files, **or**
   - use a WF-02 resource archive (SaveMyResources capture). Screenshots are refused: an image is not source code.

   State the **authority**:

   | Basis | Extraction | Requires |
   | --- | --- | --- |
   | `client_owned` | allowed | who authorised it |
   | `licensed` | allowed | the licence name and where it is |
   | `written_permission` | allowed | who gave permission, and when |
   | `study_only` | **never** | nothing: default for WF-02 captures |

   Record origin URL and commit/tag so the exact input can be found again. The archive is stored unchanged with its SHA-256; a WF-02 capture is copied, so deleting the capture later cannot change the analysis.
2. **Run the analysis.** The result is stored with its analyzer version and digest. Running it again on the same archive with the same analyzer gives the same digest; the page says whether a run was identical to the previous one.
3. **Download the analysis kit** and open it in VS Code. It contains `source/`, `analysis.json`, `findings.schema.json`, `findings.example.json` and a `CLAUDE.md` that tells Claude Code the rules: facts must cite files, assumptions are labelled, unknowns become questions, built code is not reverse-engineered into components, and study-only sources are never copied.
4. **Import `findings.json`.** All or nothing. It must carry the `scanDigest` of a scan of this source, every cited path must be in that source, and every cited line must exist. A `fact` without evidence is refused. If anything fails, nothing is imported and every problem is listed.
5. **Choose templates.** Add the scanner's template candidates to the manifest, or import analyst templates. Each keeps its basis (observed/inferred), rationale, files and evidence.
6. **Extract** (authorised sources only). Files are copied **unmodified** to the project workspace `$SCL_DATA_DIR/workspaces/<projectId>/<template-slug>/files/…`. For HTML blocks, `snippet.html` holds the block cut verbatim from its page. `PROVENANCE.json` records the source, archive SHA-256, authority, scan, and every file's source path and hash. **Download workspace** zips it, with `MANIFEST.json`, for VS Code.
7. **Build in VS Code** and record the result (passed or failed, with the command and its output). Templates with only HTML/CSS show "No build step". The app never marks a build as passed on its own.
8. **Answer the open questions.** The analysis raises them, and so can analysts and people.

## What the scanner reports

`scl.wf-03.source-analysis/v1`, defined in [src/domain/source-analysis.ts](../src/domain/source-analysis.ts):

| Section | Contents |
| --- | --- |
| `files`, `summary`, `skipped` | Every file with kind, size and SHA-256; what was not read and why (`node_modules/`, `.git/`, build folders, unsafe paths, over-limit files). |
| `frameworks` | From `package.json` and config files (observed, with version), and from markers in built output such as `__NEXT_DATA__`, Webflow/Framer attributes or `wp-content` paths (inferred). |
| `routes`, `linkedButMissing` | Next.js `app/` and `pages/` routes (groups, dynamic segments), HTML pages; internal links to pages that are not in the archive. |
| `components` | React/Vue/Svelte/Astro components, and which files import each. |
| `templateCandidates` | Next.js layouts (observed), dynamic routes as page templates (inferred), components imported by 2+ files (inferred), `header`/`nav`/`footer` with **identical markup** on 2+ pages (observed), sections sharing a class list across pages (inferred), pages sharing a top-level structure (inferred). |
| `styles` | Custom properties, breakpoints, colours, font families, `@font-face`, keyframes, transition counts, reduced-motion queries. Read as written (regex over comment-stripped CSS); preprocessor logic and the cascade are not evaluated. |
| `assets`, `missingAssets` | Images, fonts, video and audio with references, from HTML, `srcset`, inline styles and CSS `url()`; references that resolve to nothing in the archive. |
| `dependencies`, `lockfiles`, `externalResources` | `package.json` dependencies, CDN scripts with versions, every external resource and whether it has an integrity attribute. |
| `licenses`, `licenseBanners` | Licence files (type identified by wording: inferred), `package.json` licence (observed), `/*! … */` notices in bundles. |
| `responsive`, `interactions` | Viewport meta, media/container queries, `srcset`/`<picture>`; animation libraries recognised by package, import, own script file or API call; CSS animation. |
| `risks` | Each with kind, severity, basis, occurrence count and up to 10 evidence locations. Credentials are masked, never stored in full. |
| `questions` | What the scanner could not determine. |

Limits: archives up to 100 MB; at most 5,000 files, 25 MB per file and 300 MB uncompressed. Paths that escape the archive are refused, and sizes are checked before and after decompression. The analyzer has no vulnerability database: it says so and asks for `npm audit` in VS Code.

## Interfaces

All under `/api/projects/:projectId`, with the same access rules as the dashboard.

| Endpoint | Returns |
| --- | --- |
| `GET templates/manifest` | **The handoff to WF-04/05**: `scl.wf-03.template-manifest/v1` |
| `GET templates/workspace` | Workspace zip: extracted templates with `PROVENANCE.json`, plus `MANIFEST.json` |
| `GET sources/:sourceId/report` | `scl.wf-03.analysis-report/v1`: latest analysis, findings split into facts and assumptions, questions split into open and resolved, templates |
| `GET sources/:sourceId/kit` | Analysis kit zip for VS Code |
| `GET sources/:sourceId/archive` | The exact archive analysed |
| `POST sources` | Register an upload (multipart: `file`, `label`, `originUrl`, `originRef`, `basis`, `note`, `license`) |
| `POST sources/:sourceId/findings` | Import `scl.wf-03.analyst-findings/v1` (multipart `file` or JSON body). 201 with counts; 422 with every problem |

### Template manifest (`scl.wf-03.template-manifest/v1`)

Schema: `TemplateManifest` in [src/domain/wf03.ts](../src/domain/wf03.ts).

```jsonc
{
  "schema": "scl.wf-03.template-manifest/v1",
  "generatedAt": "…",
  "notices": {
    "sourceTokens": "Values as written in the source. They describe the reference, not the client's brand: WF-04 decides brand tokens.",
    "extraction": "Extracted code keeps its source's terms. …"
  },
  "project": { "id": "…", "slug": "…", "name": "…" },
  "brief": { "id": "…", "version": 2 },                          // approved WF-01 brief, or null
  "sources": [{
    "id": "…", "label": "Client site",
    "origin": { "kind": "upload", "url": "https://github.com/…", "ref": "a1b2c3d", "referenceId": null, "captureId": null },
    "archive": { "filename": "site.zip", "sizeBytes": 2048, "sha256": "…", "downloadPath": "/api/projects/…/sources/…/archive" },
    "authorization": { "basis": "client_owned", "note": "…", "license": "", "extractionAllowed": true },
    "analysis": { "scanId": "…", "analyzerVersion": "1.1.0", "digest": "…", "scannedAt": "…", "reportPath": "/api/…/report" }
  }],
  "templates": [{
    "id": "…", "slug": "header-site-header", "kind": "navigation", "name": "header.site-header",
    "description": "", "basis": "observed", "rationale": "Identical markup on 2 pages.", "origin": "scanner",
    "sourceId": "…", "scanId": "…",
    "files": [{ "path": "index.html", "sha256": "…" }],
    "pages": ["about.html", "index.html"],
    "evidence": [{ "path": "about.html", "line": 11, "excerpt": "header.site-header" }],
    "extraction": { "status": "extracted", "workspacePath": "header-site-header/", "extractedAt": "…" },
    "build": { "status": "not_applicable", "note": "" }
  }],
  "sourceTokens": [{ "sourceId": "…", "customProperties": [ … ], "colors": [ … ], "fontFamilies": [ … ], "fontFaces": [ … ], "breakpoints": [ … ] }],
  "assets": [{ "sourceId": "…", "path": "images/hero.jpg", "kind": "image", "sizeBytes": 3, "sha256": "…", "referenced": true }],
  "risks": [{ "sourceId": "…", "key": "a11y:labels", "kind": "accessibility", "severity": "high", "title": "…", "occurrences": 1 }],
  "openQuestions": [{ "sourceId": "…", "topic": "licensing", "text": "…", "origin": "analyzer" }]
}
```

How WF-04 and WF-05 should use it:
- **Only `extraction.status = "extracted"` templates have code to reuse**, and only from sources with `extractionAllowed: true`. Everything else is a pattern to rebuild, not code to copy.
- **`sourceTokens` are evidence, not brand.** WF-04 decides the client's colours, type and spacing, and may cite these as references.
- Check file hashes against `PROVENANCE.json` before using extracted files.
- `build.status` `not_verified` or `failed` means the code has not been shown to build. Treat it accordingly.
- Before relying on a template, read `openQuestions` and the `risks` for its source, especially licensing and accessibility.
- Record `sources[].analysis.digest` and `templates[].id` on whatever is built from them.

### Analyst findings (`scl.wf-03.analyst-findings/v1`)

Schema: `AnalystFindings` in [src/domain/wf03.ts](../src/domain/wf03.ts). A JSON Schema copy is in every kit as `findings.schema.json`.

```jsonc

  "findings": [
    { "basis": "fact", "topic": "styles", "statement": "…", "evidence": [{ "path": "css/site.css", "line": 1 }] },
    { "basis": "assumption", "topic": "interaction", "statement": "…", "evidence": [] }
  ],
  "questions": [{ "topic": "licensing", "text": "…" }],
  "templates": [{ "kind": "section", "name": "…", "description": "…", "basis": "inferred", "rationale": "…", "files": ["index.html"] }]

```

Topics: `framework, routes, components, styles, assets, responsive, interaction, dependencies, security, accessibility, licensing, other`.

## Rules the module enforces

- No extraction from `study_only` sources. Authority cannot be downgraded to `study_only` while extracted files exist.
- Facts must cite real files and lines in the analysed source. Invented citations reject the whole findings file.
- Screenshots cannot become sources. Extraction copies bytes verbatim and never produces an approximation.
- Credentials found in a source are reported masked and raise a question; they are never shown in full.
- Downloads are attachments with `nosniff`. Captured HTML never renders in the dashboard.

## Persistence

Migration 3 in [src/server/store/db.ts](../src/server/store/db.ts) adds `wf03_sources`, `wf03_scans` (one row per run; the stored result is the report byte for byte), `wf03_templates`, `wf03_findings` and `wf03_questions`. The code is in [src/server/store/sources.ts](../src/server/store/sources.ts) and [src/server/wf03/](../src/server/wf03/). Archives are stored under `$SCL_DATA_DIR/uploads/<projectId>/sources/`, and extracted templates under `$SCL_DATA_DIR/workspaces/<projectId>/`. Extraction writes to a temporary folder and renames it into place; if the database update then fails, the folder is removed.

## Limitations

- **The scanner is heuristic, not a compiler.** HTML is parsed properly (parse5), but CSS and JS/TS are read with patterns. It does not evaluate Sass/Less, Tailwind classes, the cascade, or runtime behaviour, and it may miss components defined in unusual ways. Interaction behaviour beyond library detection and CSS animation is for the analyst.
- **Minified bundles** (common in SaveMyResources captures) do not reveal original components; the scanner asks for the source instead.
- **Builds are not run by the app.** Extracted code is built in VS Code and the result is recorded by a person. Extracted files keep their original imports, so they may need dependencies the template does not include; the build record should say so.
- **No vulnerability database.** Dependency versions are listed, not audited.
- **Licence identification is by wording** (inferred). A person must confirm reuse rights; the open questions prompt for this.
- Analysis runs in the request (synchronously); very large archives take time.
- Same access model as WF-01: no sign-in yet (see [wf-01.md](wf-01.md#access)).
